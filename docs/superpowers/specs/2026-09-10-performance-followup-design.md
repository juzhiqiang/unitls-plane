# 性能优化收尾方案：摘要缓存与页面游标分页

## 状态与目标

本方案承接已提交的
`9c4c71f`、`9313232`。用户已同意继续收尾；本文说明新增的具体交互和实现约束，待确认后实施。本文不代表功能已经完成或压测已经通过。

本轮目标：限制账号摘要缓存长期占用，补齐写入后的缓存失效，将文件、回收站和任务页面实际接入已存在的游标接口。

## 已核实的问题

- `AccountService`
  的 Map 只有读取时检查 2 秒 TTL，没有容量上限或主动清理。过期且不再访问的用户记录会留在内存中。
- 摘要只有注销账号时失效。摘要包含文件数量、字节数和最近文件，以及活动任务、失败任务和最近任务，因此文件写入、任务状态及最近任务进度变更都需要考虑失效。
- 三个列表页仍使用 page/limit，并按 total 渲染全部页码。底层支持 cursor 和
  `includeTotal=false`，但现有页面尚未享受无深层 offset、无 COUNT 的查询路径。
- 既有测试数与构建记录属于上一批验证，不是本轮结果。Windows standalone 曾出现 symlink
  EPERM，不能据构建退出码 0 认定发布包完整可用。

## 方案比较

| 方案                                                       | 收益                                           | 代价                                                           |
| ---------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| 有界进程缓存 + 写后失效；页面改为游标上一页/下一页（推荐） | 直接处理当前缺口，复用现有 API，不新增基础设施 | 不再提供任意页码跳转；跨实例仍有短暂不一致                     |
| 只完善缓存，保留页码 UI                                    | 使用方式完全不变                               | 深分页和默认 COUNT 成本仍存在                                  |
| 共享 Redis 缓存及跨实例失效，再迁移页面                    | 可统一多实例缓存状态                           | 扩大故障处理、并发一致性和运维验证范围，不适合作为本轮最小收尾 |

## 账号摘要缓存

1. 将缓存提取为独立 Nest
   provider，通过独立模块供账号、文件和任务模块使用，避免文件模块反向依赖账号业务模块形成循环依赖。
2. 保留 2 秒成功结果缓存及同用户 in-flight 合并；缓存总条目上限为 1000，包含 pending 条目。触达上限时淘汰最久未使用条目。淘汰不取消调用方正在等待的请求；极端容量压力下允许被淘汰用户发起新的数据库读取，不无限保留请求索引。
3. 每 5 秒清理过期的已完成条目；定时器不阻止进程退出，在模块销毁时停止并释放缓存。pending 请求不因普通 TTL 到期就失去合并能力，但仍受容量上限限制。
4. 使用条目身份校验，确保失效、淘汰之后的旧 Promise 不能回填缓存，也不能删除同用户的新缓存。失败请求不得缓存为正常结果。
5. 文件上传和任务输出文件入库、软删除、恢复、永久删除与清理，以及任务创建、删除、状态与摘要可见进度变更，在数据库提交成功后按所属用户失效。覆盖单条、批量、Worker 和清理路径；批量部分成功时，已经成功的写入仍须失效。匿名记录不建立用户缓存。
6. 注销账号开始和完成时继续失效。不能在事务提交前仅清一次缓存，避免提交前读取到旧数据库状态后被重新缓存。
7. 本轮仍为进程内缓存，不引入跨实例消息机制。同进程写入后的新读取不复用失效前缓存；已开始的读取不承诺线性一致性。其他实例的成功缓存仍受 2 秒 TTL 约束，但前端显示何时更新还取决于下次刷新，不能承诺界面最多延迟 2 秒。

## 页面游标分页

1. 保持已核实的现有每页数量：文件页 12 条、回收站 12 条、任务页 20 条，不顺带改变密度。
2. 首次请求传 `cursor=''` 和
   `includeTotal=false`；下一页使用响应的 nextCursor，不通过页号计算 offset。旧 page/limit
   API 保留兼容。
3. 以共用分页 hook 管理已访问游标历史，界面显示“上一页 / 第 N 页 / 下一页”，并提供返回首页。没有 nextCursor 时禁用下一页；第一页禁用上一页。不显示总页数，不渲染全部页码，不将
   `total: null` 显示为 0 条。
4. 筛选或搜索改变时清空游标历史，立即以新筛选请求首页，避免旧游标与新筛选组合导致 400。账号切换不复用前一个账号的分页历史。
5. 翻页期间禁用重复导航，不使用上一页的 nextCursor 推进新页。请求失败保留返回能力并提供重试；不得将错误显示为正常空列表。
6. 翻页和筛选时清理选择与确认状态，避免批量操作隐藏页的文件。删除、恢复或清空成功后重置到首页，避免当前页被清空后停留在不可理解的空白页。任务轮询保留当前页，不随每次状态变化强制返回首页。
7. 中文、英文文案同步维护。不调整视觉风格，不改工具页。
8. 游标分页不是快照；并发新增和删除可能改变回访页面内容。不为本轮增加跨请求快照一致性。

## 验证与交付

- 先写失败测试，再实现缓存容量、过期清理、并发合并、错误重试、失效期间旧请求迟到等行为。
- 验证实际写入路径触发失效，特别是事务提交、批量部分成功、Worker 输出和清理任务，不只测试缓存类自身。
- 页面或 hook 测试覆盖首次 cursor 请求、前进/后退、筛选重置、末页、请求失败、连续点击、删除后返回首页，以及 nullable
  total。
- 运行 API/Web/packages 回归、相关 lint 和构建。API 修改后重新导出 OpenAPI 并核对 client；本轮不预期改变接口或数据库 schema。
- 整理审计文档顶部的最新状态，历史记录明确标注，不把旧测试数当成新验证。
- 大表基准仅使用隔离的合成数据，不向现有业务表灌测试数据。记录数据规模、查询计划、P50/P95、offset/cursor 与带/不带 COUNT 对照；环境不具备条件时如实列为未执行。
- 大文件测试记录文件大小、像素/页数、并发、RSS/heap/external 和浏览器长任务；未经实际测量不承诺内存峰值或 FPS 达标。本地结果不能替代 staging/生产规模验收。
- 验证后的变更按项目规则创建中文 Git 提交，不推送，不改服务器，不提交日志与截图。

## 明确不在本轮代码范围

- Multer 流式上传、按字节配额控制、处理器解码架构重写。
- PDF 拆分/重排工具页的全面窗口化。
- Redis 共享摘要缓存、集群级一致性。
- Windows 权限设置或发布环境修改；standalone 完整性仍作为独立待验收项。

完成本方案也不等于整个项目的全部性能风险已经消除。
