🎯 设计原则（正确理解）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
采用 **数据库软删除 + MinIO保留** 策略

✅ 数据库层：删除23条不适合的记录
   → API不返回这些姿势
   → 前端无法获取ID
   → 用户看不到这些内容

✅ MinIO存储层：保留所有116个文件
   → 包括已删除记录对应的46个文件
   → 文件继续存储，便于将来管理
   → 可随时恢复或完全删除

📊 当前状态
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
层级           可见数量    总存储量    说明
────────────────────────────────────────────────────────────
数据库记录         38         38     只保留适合电商的
MinIO文件          -         116     保留所有图片
前端显示           38         -      由数据库控制
────────────────────────────────────────────────────────────

🔒 安全机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1️⃣ API层控制
   GET /tasks/ai-try-on/references?kind=pose
   → 只返回数据库中存在的38条记录
   → 已删除的23个姿势不会返回

2️⃣ 前端访问控制
   → 没有记录ID = 无法构造URL
   → 没有URL = 无法显示图片
   → 用户完全看不到已删除内容

3️⃣ MinIO文件保留
   → 文件静默存储
   → 不影响前端展示
   → 便于内容管理

💡 为什么这样设计？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ 内容安全
   前端用户完全看不到成人内容姿势
   
✅ 数据保留
   如果将来需要恢复或用于其他场景
   不需要重新下载图片
   
✅ 管理灵活
   - 需要恢复？INSERT数据库记录即可
   - 需要删除？可单独清理MinIO文件
   - 方便审计和内容分级

✅ 成本优化
   MinIO存储成本低
   删除重新下载反而麻烦

🔄 恢复姿势示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  slug, kind, title_zh, ..., license_reviewed_at
) VALUES (
  'pose-xxx', 'pose', '某姿势', ..., NOW()
);
