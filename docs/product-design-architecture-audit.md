# Utils Plane 产品设计与架构审计建议

> 审计视角：高级产品设计师 + 架构顾问  
> 范围：UI、信息架构、核心工具流程、文件/任务管理、后端安全边界、工程化与上线准备度

## 整体评分

| 维度 | 评分 | 判断 |
|---|---:|---|
| 产品定位 | 7/10 | 工具平台方向清晰，图片/PDF/字体三个主类合理 |
| 信息架构 | 6/10 | 主导航清楚，但 Dashboard、文件、任务与工具流没有形成闭环 |
| 视觉系统 | 7/10 | 有克制、工具感、低噪声的基础，但部分页面密度和状态设计不足 |
| 交互体验 | 6/10 | 上传、配置、处理、下载流程已成型，但不同工具页体验不统一 |
| 功能完整度 | 6/10 | PDF 功能面广，但管理、统计、清理、安全、任务可观测性不足 |
| 可访问性 | 5/10 | 图标按钮、状态提示、键盘操作、aria 文案还需要系统补齐 |
| 工程成熟度 | 6/10 | Monorepo 架构不错，测试已有基础，但 lint、类型、OpenAPI 漂移需要治理 |
| 上线准备度 | 5/10 | 目前更像功能原型/内测版，不建议直接公开上线 |

## 设计审计表

| 模块 | 当前表现 | 主要问题 | 高级设计建议 | 优先级 |
|---|---|---|---|---|
| 首页/Marketing | 有品牌感，使用网格、弱动效、工具入口 | 文案 CTA 指向 `/docs`，但项目里未见对应页面；营销承诺“本地处理/隐私”与部分服务端处理逻辑不完全一致 | 把首页改成“可立即使用的工具入口”，减少抽象宣传；明确区分“本地处理”和“服务端处理” | 高 |
| 主导航 | 左侧工具分类清楚，图标选择合理 | Dashboard 没有在侧边栏里出现，但 Header 面包屑把它当 home；用户路径略断 | 侧边栏加入 Dashboard；把“工具、文件、任务、设置”形成完整工作台结构 | 高 |
| Dashboard | 目前只有 3 个写死为 0 的统计卡片 | 没有真实价值，像未完成页面 | 改成运营型首页：最近任务、失败任务、最近文件、存储用量、快捷工具、处理成功率 | 高 |
| PDF 工具首页 | 工具覆盖完整，网格入口清晰 | 11 个工具平铺，缺少分组和推荐路径 | 按“整理、转换、安全、优化”分组；展示最近使用/常用工具；给高频功能更高权重 | 中 |
| Image 工具首页 | 简洁直接 | 只有两个入口，视觉重量弱于 PDF；缺少批量场景说明 | 加入“压缩、转换、批量处理、预览对比”的能力表达；保持工具页不是营销页 | 中 |
| Font 页面 | 有预览、格式选择、子集化，方向专业 | 字体转换需要登录，前面没有足够预期提示；错误和成功状态偏弱 | 在上传后明确显示“需登录/将上传服务器处理”；结果区展示原格式、目标格式、文件大小变化 | 中 |
| 文件管理 | 有搜索、筛选、网格/列表、批量删除 | 网格卡片缺少文件类型视觉预览；批量操作区不够稳定；下载/删除按钮缺少 aria label | 图片显示缩略图，PDF 显示页数/封面，字体显示样张；批量操作固定为 toolbar 状态 | 高 |
| 任务记录 | 表格结构较好，状态、进度、重试都有 | 任务详情展示 ID 和 JSON，对普通用户不友好；持续时间里有疑似乱码占位 | 详情面板改成“输入文件、输出文件、参数摘要、失败原因、人类可读建议” | 高 |
| 上传组件 | 简洁、符合工具产品气质 | 空状态单薄；上传拒绝错误只是技术 message；没有显示容量限制的结构化信息 | Dropzone 里固定显示支持格式、最大大小、是否本地处理；错误翻译成用户语言 | 高 |
| 处理进度 | 细线 progress 很符合设计系统 | 长任务缺少阶段感，只有百分比；失败后恢复路径不明显 | 进度增加阶段标签：上传中、排队中、处理中、生成结果；失败给“重试/更换文件/查看原因” | 高 |
| PDF 预览/选择页 | 有缩略图选择，是正确方向 | 缩略图加载时只显示 `...`；大 PDF 下分页/性能/选择反馈可能吃力 | 加 skeleton、页码范围选择、全选/反选、已选数量；大文档虚拟滚动 | 中 |
| 表单控件 | 基本克制，符合低噪声工具风格 | range、number input、segment 控件样式不完全统一 | 建立统一控件规范：Segment、Stepper、Slider、Switch、FileMeta、ResultPanel | 中 |
| 状态文案 | 多语言框架存在 | 当前读取到中文资源疑似乱码或编码显示异常；若真实页面如此会严重损害可信度 | 全量检查 `messages/zh.json` UTF-8、JSON 合法性和真实渲染；文案走产品化重写 | 高 |
| 可访问性 | 有部分 title/label | 图标按钮多处缺少明确 aria-label；点击卡片含 checkbox 容易事件冲突 | 所有 icon button 加 aria-label；表格/批量选择支持键盘；状态变化用 toast/live region | 中 |
| 移动端 | 多处有响应式布局 | 文件表格、任务筛选、PDF 缩略图在小屏会比较挤 | 移动端优先“卡片流 + 底部操作栏”，筛选收进 sheet | 中 |
| 视觉一致性 | 全局颜色、边框、字号已有系统 | 工具页之间最大宽度、卡片形式、结果区位置不完全一致 | 做统一页面模板：Header、Dropzone、ConfigPanel、PreviewPanel、ResultPanel、HistoryHint | 高 |
| 安全感设计 | 有隐私诉求 | 实际服务端处理、登录要求、文件过期规则没有在 UI 中透明表达 | 每个工具显示处理位置、文件保留时间、是否上传服务器、登录原因 | 高 |

## 功能与架构审计表

| 领域 | 发现 | 风险 | 建议 | 优先级 |
|---|---|---|---|---|
| 文件权限 | 下载接口公开，私有文件访问边界不够严 | 文件 ID 泄露后可能被下载 | 登录用户文件下载必须校验 owner；匿名文件使用短期 signed token | P0 |
| 任务状态 | `/tasks/:id/status` 公开查询 | 任务状态、错误、输出文件 ID 泄露 | 任务轮询使用 task token，登录任务校验 owner | P0 |
| 清理任务 | Cleanup processor 还是占位；过期查询条件疑似反向 | 匿名文件无法按期清理，存储成本上升 | 实现清理任务；用 `expiresAt <= now`；加入测试 | P0 |
| OpenAPI 类型 | 前端多处 `as any` 调接口 | API 改动时前端静默坏掉 | CI 中强制 `openapi:export -> api-client generate -> typecheck` | P1 |
| 任务配置校验 | Processor 内部分散校验 | 不同工具参数可能进入非法状态 | 为每种 task type 建立 Zod config schema | P1 |
| 工程门禁 | `bun run lint` 被 CRLF/Prettier 卡住 | 团队无法稳定检查质量 | 明确 `.gitattributes` 和 Prettier `endOfLine` 策略 | P1 |
| 观测性 | 有 error tracker，但任务级监控弱 | 长任务失败难定位 | 记录任务阶段、耗时、输入大小、失败码、worker 日志关联 ID | P1 |
| 配额系统 | 仅有文件大小限制 | 匿名批量消耗资源 | 加用户/匿名每日任务数、并发数、总存储、队列优先级 | P1 |
| 文件生命周期 | 有 trash，但 UI/后端策略不完整 | 删除、过期、恢复规则不透明 | 统一文件状态：active/trash/expired/deleted；UI 显示剩余保留时间 | P2 |
| Dashboard API | 无聚合统计接口 | 首页无法产品化 | 新增 `/me/summary` 或 dashboard endpoint | P2 |

## 建议改版优先级

| 阶段 | 目标 | 具体事项 |
|---|---|---|
| 第 1 阶段 | 先补安全和可信度 | 修文件下载权限、任务状态权限、清理任务、中文文案编码、lint 换行策略 |
| 第 2 阶段 | 统一工具体验 | 抽象统一工具工作流：上传、配置、预览、处理、结果、历史 |
| 第 3 阶段 | 提升专业感 | 重做 Dashboard、任务详情、文件预览、错误恢复、处理位置说明 |
| 第 4 阶段 | 准备上线 | 加配额、观测、用户存储统计、失败率监控、OpenAPI CI |

## 关键设计原则

| 原则 | 说明 |
|---|---|
| 工具优先 | 首屏应让用户进入真实工具，而不是停留在宣传信息 |
| 可信透明 | 明确告诉用户文件是否上传、保留多久、是否需要登录、失败后怎么办 |
| 状态可见 | 上传、排队、处理中、生成结果、失败、重试都要有稳定反馈 |
| 流程统一 | 图片、PDF、字体工具都应共享同一套任务体验，而不是各自实现一套 |
| 专业克制 | 保持低噪声、低阴影、线框、mono 信息层级，但提升数据密度和操作确定性 |

## 一句话结论

这个项目已经有“工具平台”的骨架和审美方向，但现在最大短板不是页面不够漂亮，而是“可信度体验”还不够完整：用户需要清楚知道文件在哪里处理、是否安全、任务发生了什么、失败后怎么办、结果在哪里管理。先把这些打磨好，视觉质感会自然上一个台阶。
