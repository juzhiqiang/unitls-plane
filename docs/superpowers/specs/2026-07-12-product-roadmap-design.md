# Utils-Plane 产品与技术规划设计

## 背景

Utils-Plane 当前已经具备完整的文件处理平台雏形：Next.js 前端、NestJS
API、Better-Auth、PostgreSQL、Redis、MinIO、BullMQ、文件管理、任务历史，以及图片、PDF、字体等工具模块。近期新增了长图拼接、GIF/APNG 动图工具、Markdown
/ Word 转 PDF、Docker 离线部署文档和登录商业版预留能力。

当前阶段的主要风险不是功能数量不足，而是产品定位、权益体系和技术边界继续分散。如果继续单纯堆工具，后续商业化、维护和部署都会变重。因此本规划建议先把产品骨架整理成可收费、可扩展、可私有部署的结构，再按重点工具继续扩展。

## 推荐定位

Utils-Plane 推荐采用“双轨”定位：

1. **个人与小团队效率工具**：面向创作者、运营、电商、小团队，主打本地优先、批量处理、任务历史、模板和高限制。
2. **私有化部署工具箱**：面向内网、站长、企业自部署场景，主打 Docker 离线包、稳定升级、保留数据、可控文件处理和部署文档。

一句话定位：

> 面向个人、小团队和内网场景的文件处理工具平台，主打本地优先、隐私清晰、批量处理和可私有部署。

## 产品原则

- **本地优先说清楚**：每个工具都明确展示本地处理、服务端处理、登录要求和文件保存策略。
- **免费功能能独立完成任务**：免费用户可以完成基础图片、动图、长图和 Markdown 本地 PDF 等高频任务。
- **登录权益服务工作流**：登录不是硬挡入口，而是开放历史、批量、高限制、模板、云端处理和账户文件。
- **商业能力提前统一**：当前“登录商业版”与未来付费版使用同一套权益判断，避免未来重做。
- **私有部署可维护**：Docker 离线包、升级、回滚、健康检查和版本信息应成为产品能力，而不是临时运维说明。

## 商业化分层

### 免费版

免费版用于获得流量和信任，重点保留高频本地能力：

- 图片压缩、格式转换、基础水印。
- 长图基础拼接。
- GIF 基础制作与简单压缩。
- Markdown 在线编辑、预览和本地导出 PDF。
- 匿名文件短期处理，使用较低上传大小和频率限制。

### 登录商业预览版

登录后开放未来可收费的核心能力。当前不必接支付，但权益边界必须真实存在：

- 更高上传大小、更多批量数量和更高任务频率。
- 账户文件、任务历史、失败恢复和重新处理。
- APNG、高级 GIF 压缩、更大动图尺寸、更多帧数。
- 长图商业模板、批量宽度、品牌页尾、预设模板。
- 服务端 Markdown / Word 高质量导出。
- 证件照生成、AI 精修和规格模板。

### 未来付费版

付费版不在本规划内立即实现支付，但代码结构要能自然接入：

- **个人 Pro**：高限制、批量、历史、模板、云端任务。
- **Team**：团队空间、共享文件、成员管理、统一文件保留策略。
- **Private Deploy**：离线部署授权、版本包、部署支持、升级手册和内网能力。

## 产品阶段规划

### 阶段 1：打磨现有工具转化

目标：让用户一眼理解平台能做什么、文件在哪里处理、为什么值得登录。

建议：

- 将工具入口按“图片”“PDF”“动图”“文档”“字体”重新整理。
- 每个工具页固定展示处理方式、是否登录、保存时间和失败恢复说明。
- 登录提示只出现在高级功能或服务端能力旁边，不阻挡免费本地工具。
- 结果区统一提供下载、再次处理、保存到文件、查看任务历史等路径。

### 阶段 2：补齐权益基础

目标：把“登录商业版”和未来付费版打通，避免每个工具各自判断。

建议：

- 建立统一权益层，支持 `free`、`signed_in`、`pro_preview`、未来 `pro`。
- 把上传大小、批量数量、输出尺寸、任务频率、服务端导出等限制集中定义。
- 前端和后端共用同一类 feature key，例如 `image.animation.apng`、`pdf.document.serverExport`。
- 后端任务创建和文件上传也做权益校验，不能只依赖前端隐藏按钮。

### 阶段 3：增强工作流功能

目标：让登录用户从一次性工具使用进入持续工作流。

建议：

- 文件管理增加按工具类型、来源任务、输出类型筛选。
- 任务页支持重试、复制配置、重新处理和结果文件跳转。
- 图片模块增加常用预设：电商长图、小红书长图、公众号封面、证件照规格。
- PDF 模块沉淀“文档工作台”：Markdown 编辑、预览、导出历史、模板。

### 阶段 4：私有化部署产品化

目标：把已经存在的 Docker 离线部署能力包装成可交付能力。

建议：

- 增加服务健康与版本信息页面或接口，展示 API、Web、PostgreSQL、Redis、MinIO、LibreOffice 状态。
- 在构建产物中暴露版本号、commit、构建时间和 release 标识。
- 继续扩展 `docs/docker-offline-deployment.md`，覆盖首次部署、更新、回滚、备份和常见故障。
- 为私有部署保留 license / feature flag 接入点，但首版不实现复杂授权。

## 技术优化建议

### 统一权益系统

建议新增权益判断边界，而不是在工具页里散落 `requiresLogin` 和手写判断。

目标接口形态：

```ts
canUseFeature(user, 'image.animation.apng');
canUseFeature(user, 'pdf.document.serverExport');
getLimit(user, 'upload.maxFileSize');
getLimit(user, 'image.animation.maxFrames');
```

前端用于展示、禁用、升级提示；后端用于任务创建、文件上传和处理限制校验。

### 工具配置中心升级

现有 `tool-metadata.ts` 可以扩展为更完整的工具能力配置：

- `featureKey`
- `processingModes`
- `freeLimits`
- `signedInLimits`
- `commercialFeatures`
- `acceptedMimeTypes`
- `outputMimeTypes`

收益是首页、工具页、登录提示、任务创建和文档可以逐步复用同一份元数据。

### 任务处理器注册表

当前任务类型已经覆盖图片、PDF、字体、证件照和文档转 PDF。后续建议引入任务处理器注册表，减少 switch 扩散。

每个任务声明：

- 任务类型。
- 所属队列。
- 输入文件数量和 mime 限制。
- 权益要求。
- 处理器函数。
- 输出 mime 和文件命名策略。

这样新增工具时主要新增一个 handler，而不是同时修改 DTO、validators、队列路由、处理器分支和前端提示。

### 工具页模板化

图片、PDF、动图、文档工具存在重复结构，但不建议抽象成过大的万能工具页。建议沉淀小而稳定的模块：

- 上传区。
- 参数区。
- 预览区。
- 结果区。
- 登录商业提示。
- 错误恢复。
- 任务状态轮询。

每个工具仍保留独立页面和业务逻辑，避免过度抽象。

### 可观测性与部署诊断

商业化和私有部署需要快速判断问题来源：

- 任务失败原因标准化。
- 每类任务记录耗时、输入大小、输出大小、失败原因。
- 健康检查覆盖 PostgreSQL、Redis、MinIO、LibreOffice。
- Docker 构建和运行时显示版本号、commit 和 release。

### 测试重点

优先补覆盖以下风险点：

- 权益判断矩阵。
- 文件 mime 白名单。
- 任务类型到队列的路由。
- Markdown / Word 转 PDF fallback。
- 登录商业功能在前端显示和后端拦截的一致性。
- Docker 部署文档中的关键命令可复制、无破坏性。

## 推荐近期落地顺序

近期最值得执行的顺序：

1. 设计并实现统一权益层，把登录商业版和未来付费能力固定下来。
2. 优化工具入口和工具页商业提示，统一展示处理方式和登录收益。
3. 增加服务健康与版本信息，服务 Docker 离线部署和私有化交付。
4. 收敛任务处理器注册方式，减少后续新增工具时的多处修改。

## 暂不建议优先做

- 立即接支付系统：权益边界还没完全稳定，过早接支付会增加迁移成本。
- 一口气新增大量工具：当前更需要统一入口、权益和任务边界。
- 做重团队协作：团队空间、成员权限可以预留，但不应早于个人 Pro 和私有部署基础。
- 全仓大重构：优先围绕权益、工具元数据和任务注册表做局部优化。

## 成功标准

规划落地后，应达到：

- 用户能理解哪些功能免费、哪些登录后更强、哪些未来可付费。
- 新增一个商业能力时，前端展示、后端校验、限制配置和文案不再散落。
- Docker 私有部署可以稳定更新、保留数据并快速排查问题。
- 工具数量继续增加时，代码复杂度增长速度明显下降。

## 后续拆分建议

本规划应拆成独立实施规格，而不是一次性全部实现：

1. 权益系统设计与实现。
2. 工具入口和商业提示优化。
3. 服务健康与版本信息。
4. 任务处理器注册表。
5. 文档工作台增强。

建议先从 **权益系统设计与实现** 开始，因为它会影响后续所有商业能力。

## 附录：Markdown / Word 转 PDF 稳定性与多页预览设计（2026-07-18）

### 背景与目标

Markdown /
Word 转 PDF 当前有两个用户可见问题：开发环境导出正常，线上可能出现首页空白或正文缺失；结果预览固定只渲染第一页，多页 PDF 无法翻页。调查确认开发环境未安装 LibreOffice 时走
`pdf-lib`
fallback，生产组合镜像安装 LibreOffice 后走 HTML 到 Writer 的另一条链路；`PdfResultPreview`
当前固定调用 `renderPdfPage(doc, 1, 0.45)`。

本附录的目标是统一服务端输出质量，并让结果预览支持翻页和完整缩略图；不改变本地 Markdown 预览、本地打印导出、DOCX 输入协议、任务权限、文件保留策略或遥测边界，也不引入 Chromium。

### 服务端转换方案

`PdfService.documentToPdf` 继续以 LibreOffice 为首选：

1. 在任务临时目录创建独立 LibreOffice user profile，通过 `-env:UserInstallation=file://...`
   传入，避免并发任务共享默认 profile 造成锁竞争和旧状态污染。
2. 生成包含 UTF-8、`lang="zh-CN"`、正文容器和 A4 页面样式的 Writer 兼容 HTML，避免浏览器专属 CSS，并继续使用
   `marked` 和现有安全清理。
3. 转换后按页提取文本：移除开头连续空白页；正文全部为空时失败；再从 Markdown 提取去除格式标记的标题和正文片段，确认关键片段出现在 PDF 文本中，拒绝“只有少量文字但正文丢失”的输出。
4. 校验失败时重试一次兼容 filter：第一次使用显式 `pdf:writer_pdf_Export`，第二次使用默认 `pdf`
   filter；两次都使用独立 profile 和新的输出目录。全部失败后才使用现有 `renderMarkdownFallbackPdf`。

只移除前置空白页，不删除用户有意保留的中间空白页。内部命令、路径和校验细节不返回客户端。

### PDF 结果预览方案

`PdfResultPreview`
保存 PDF 总页数、当前页和每页缩略图 canvas。主预览提供上一页、下一页和“当前页 / 总页数”；第一页和最后一页分别禁用对应按钮。所有页面按有限并发生成低倍率缩略图，以按钮网格或缩略图栏展示，点击后切换当前页并高亮选中项。主页面和缩略图均使用自然宽高、`object-contain`
与可滚动边界，禁止固定高度裁切；组件卸载时取消未完成渲染。新增按钮、页码和 `aria-label`
文案同步维护中英文翻译。

PDF 加载失败时保留错误状态；单页缩略图失败不影响其他页面；所有服务端转换方式都失败时沿用任务失败机制，不返回损坏文件。

### 回归测试与验收

- API：覆盖首页空白但后续有正文、正文片段缺失、正常多页输出，以及转换命令包含独立 profile 参数。
- Web：覆盖三页 PDF 的缩略图数量、上一页/下一页边界、缩略图切页、单页状态和组件卸载取消。
- 验收：同一份包含标题、段落、列表和多页正文的 Markdown 在开发与生产链路中都能看到完整正文且第一页非空；结果预览可浏览所有页面，缩略图显示完整页面轮廓且无裁切或重叠。

## 附录：Markdown 编辑器固定高度与源码高亮设计（2026-07-19）

### 背景与目标

当前 `MarkdownEditor` 只使用普通
`textarea`，编辑区域设置的是最小高度且允许纵向拖拽。长文档会持续撑高工作台，Markdown 标题、列表、引用、链接、强调和代码等源码类型也没有视觉区分。

本次调整只改变 Markdown 源码编辑体验：编辑器固定为 `520px`
高度，超出范围后在编辑区内部滚动；Markdown 源码按语法 token 上色。输入值、任务参数、本地预览、服务端转换和原始 Markdown 内容均保持不变。

### 编辑器结构

继续保留原生 `textarea` 作为唯一输入控件，在同一内容区域内叠加一个只读高亮层：

1. 外层编辑视口固定为 `520px`，移除 `resize-y`，不再随内容增长。
2. `textarea` 负责输入、光标、选区、复制粘贴和键盘行为；长文档纵向滚动，长行横向滚动。
3. 高亮层使用与 `textarea` 完全一致的字体、字号、行高、空白处理和内边距，位于输入层下方并设置
   `aria-hidden="true"` 与 `pointer-events: none`。
4. 左侧行号、高亮层和 `textarea` 同步 `scrollTop`；高亮层同时同步
   `scrollLeft`，保证长行滚动时字符仍对齐。
5. `textarea`
   的文字本身透明，只保留可见光标和选区；实际可见文字由高亮层绘制。禁用状态沿用现有透明度反馈。

### Markdown 高亮方案

使用项目已有的
`highlight.js`，只注册 Markdown 语言，避免引入新的编辑器依赖或加载全部语言包。高亮结果使用现有
`.hljs-*` 设计变量，因此浅色和深色模式自动保持一致。

高亮至少覆盖标题、列表符号、引用、链接、强调、行内代码、代码围栏和 HTML 标签。高亮层只处理显示结果，不修改
`value`，`onChange` 仍原样返回用户输入。

不采用
`contenteditable`，因为其光标、输入法、粘贴和撤销行为更难稳定；也不使用独立的编辑器框架，避免为本次窄范围需求增加体积和新的状态边界。

### 错误与边界处理

- 空内容仍显示一行可编辑区域和第一行行号。
- 高亮失败时回退为经过 HTML 转义的纯文本显示，不能影响输入。
- 高亮输出只来自 `highlight.js` 对源码的转义结果，不执行用户输入的 HTML。
- 输入层和高亮层必须保持相同换行策略；使用不自动折行的源码模式和横向滚动，避免叠层错位。

### 回归测试与验收

- 测试固定高度、不可拖拽和编辑区内部滚动类名。
- 测试 Markdown 标题、列表、链接和代码等内容产生对应 `.hljs-*` token。
- 测试高亮层为只读、不可交互且不进入无障碍树。
- 测试滚动时行号与高亮层同步纵向位置，高亮层同步横向位置。
- 测试 `onChange` 仍返回未经转换的原始 Markdown。
- 验收时在桌面和移动宽度下输入长文档及长行，编辑器高度保持不变，滚动条可用，光标、选区和高亮字符位置不发生可见偏移。
